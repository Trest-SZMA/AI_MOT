# Алгоритмы сервиса реализации — полное описание

Состояние на 06.08.2026, сборка `20260806-155914`. Документ в двух частях:

* **Часть I — внутренняя логика.** Что сервис делает и по каким правилам, на языке
  предметной области. Читается без кода; каждое правило — с причиной, по которой
  оно именно такое.
* **Часть II — машинная логика.** Как это исполняется: проходы, структуры данных,
  ключи, инварианты, сложность, форматы. Читается вместе с кодом.

Опорные цифры, к которым привязаны примеры: продано **537 518,952 т**, период
2021-10-31 … 2026-08-05, 304 388 строк движений (из 304 774 строк регистра), 7 869 позиций, 1 072 проекта.

# ЧАСТЬ I. ВНУТРЕННЯЯ ЛОГИКА

## 1. Задача

Ответить на вопрос: **что, сколько, по какому бизнес-плану и серии продано, и как
двигался металл**. Готового отчёта в 1С нет, SQL-доступа нет — есть файловые
выгрузки регистра «Товары на складах» и четыре справочника.

Главная трудность в том, что **серия проставлена не везде**. Из 537 518,952 т
проданного серия записана в самой строке 1С только у 27,2 %. Остальное сервис
**восстанавливает** — по партии, по документу, по наследованию при переработке,
по имени склада. Ещё 29 % восстановить не удаётся, и они честно показаны как
«БЕЗ СЕРИИ», а не размазаны по планам.

Всё остальное в системе — следствие этой задачи.

## 2. Что считается продажей

Продажа — строка расхода, где регистратор начинается с «Реализация товаров и
услуг». Перемещение, переработка, внутреннее потребление, списание, возврат и
пересортица продажей не являются.

**Внутренний оборот исключён.** До 01.03.2024 купленное вставало на «Цех»
(организация МЕТАЛЛОЛОМ 1), перепродавалось своей же организации «Проект БАЗЫ» и
только потом внешнему покупателю. Такие «реализации» — 4 723 строки — продажей не
считаются, иначе тоннаж задваивается. То же правило применено к третьей
организации «ИВЦ Металлолом», появившейся в выгрузке 06.08.2026.

## 3. Бизнес-план — это ПРОЕКТ, а не номер договора

Идентичность серии задаёт **ПроектГуид** из справочника серий: варианты «… V» и
«… VS» — одна серия, сведённая в 1С в один проект. Договор 1291032 — это восемь
разных проектов.

Ведущий номер серии (3–4 цифры) ключом быть **не может**: он склеивал 18 проектов
«1291032 … СП N» в одну «серию 1291». Запасное правило — поиск по ведущему
номеру, но только когда номер однозначен во всём справочнике.

## 4. Каскад восстановления серии — десять ступеней

Для каждой строки реализации правила проверяются сверху вниз, первое сработавшее
выигрывает. У результата остаётся **бейдж** — метка происхождения, по которой
видно, факт это или реконструкция.

| # | Правило | Бейдж |
|---|---|---|
| 0 | ручная привязка из `overrides.json` | ручная |
| 1 | **серия записана в самой строке 1С** — высший приоритет, никаких расчётов | 1С |
| 2 | склад закреплён за единственной серией 1С | склад |
| 3 | смешанный лот: точное количество → аллокация по ёмкости → деление | док / доля |
| 4 | перемещение, приходная сторона: серия с расходной стороны того же документа и **той же партии** | док |
| 5 | карта «партия + код» → серия по всей выгрузке | док |
| 6 | наследование при переработке (четыре ограничения) | переработка |
| 7 | единственная серия, приходившая на этот склад под этим кодом | вероятно |
| 8 | договор и номер БП из имени договорной площадки | площадка |
| 9 | пометки ВВОД ОСТАТКОВ / ИЗЛИШКИ | ввод |
| 10 | иначе — БЕЗ СЕРИИ | нет |

При агрегации нескольких строк в позицию побеждает **худший** бейдж: если хоть
что-то восстановлено предположительно, вся позиция помечена так.

Распределение по тоннажу: 1С 27,2 % · площадка 35,0 % · переработка 5,4 % ·
док 3,3 % · доля 0,04 % · нет 29,1 %.

## 5. Лоты

**Ключ лота = тип документа + номер.** Только номер склеивал разные документы:
«Приобретение РУМЛ-000146» (закупка трубы в Когалыме) и «Производство без заказа
РУМЛ-000146» (выпуск лома на Усинске) — разные документы с одним номером. По всей
базе это давало около 19 000 т ложной привязки. Для документов переработки в ключ
входит ещё и **дата**: номера повторяются по годам.

**Пустое описание партии лотом не считается.** Ключ «пусто + код» склеивал все
безпартийные приходы кода по всей базе — до 13 тыс. т на один ключ, и «привязка по
документу» превращалась в фикцию «этот код когда-то где-то приходил с такой
серией». Таких строк реализации 18 315, они остаются БЕЗ СЕРИИ.

**Перемещение лот не тратит.** «Уехало» компенсируется «приехало» того же лота, и
один лот может переезжать несколько раз. Когда перемещение считалось расходом
лота, ёмкость выедалась вдвое и раскладка вырождалась в доминирующую серию.

## 6. Смешанные лоты — без дробных хвостов

В 488 лотах приход содержит несколько серий. Порядок разбора:

1. **точное количество** — строка продажи 0,008 забирает компонент 0,008;
2. **аллокация по ёмкости** — компонент, у которого хватает неизрасходованного
   остатка, отдаёт строку целиком; строки идут по дате;
3. только если строка не влезает ни в один компонент — **деление** с бейджем
   «доля» и записью в «Проблемы».

«Победитель забирает всё» отдавал серии 1578 чужие 8 кг. Пропорциональное деление
давало верные итоги, но размазывало документы: в одном документе появлялись суммы
0,439 / 0,008 / 0,005, которых в 1С нет.

Компоненты меньше 1 % и всё сверх четырёх компонент сворачиваются в доминирующую
серию — иначе лот на 23–28 серий дробит каждую продажу на десятки строк.

## 7. Переработка

### Наследование серии — четыре ограничения

Документы «Производство без заказа» и «Сборка (разборка)» здесь не спецификации
на изделие, а массовые суточные документы: десятки материалов на разных складах.
Наивный «argmax по документу» приписывал БП 1578 медную катанку 125 819 т, свинец
и статоры ПЭД. Поэтому:

1. **Локальность по складу.** Выпуск наследует серию от сырья того же склада;
   сырьё всего документа берётся, только если на складе выпуска сырья нет.
2. **Доминирование ≥ 50 %.** Иначе выпуск — смесь и идёт БЕЗ СЕРИИ.
3. **Доля считается от ВСЕГО сырья**, а не от опознанного: иначе документ, где
   90 % сырья без серии и 10 % серии X, давал X долю 100 %.
4. **Присутствие серии на складе.** Наследовать можно только туда, где серия
   фактически была.

Документ переработки опознаётся по **регистратору**, а не по типу партии: под
условие «партия — сборка» попадала строка ПРОДАЖИ.

### Где тоннаж рождается из штук

Обычно «в резку» и «из резки» гасят друг друга — тот же металл, другая форма. Но
если **сырьё документа не имеет тоннажа вовсе, а выпуск имеет** — это появление
тонн: разобрали ёмкость (1 шт) → получили 40 т лома. Такой выпуск считается
приходом. Сырьё и выпуск сопоставляются внутри одного документа **по серии,
которую написала сама 1С**. Масштаб: 783 пары «документ + серия», 1 805,610 т.

## 8. Перемещения

Приходная сторона берёт серию с расходной стороны **того же документа и той же
партии**. Партия в ключе обязательна: документ РУ00-004626 двигал одну
номенклатуру сразу под пятью сериями, и ключ без партии отдавал все приходы
доминирующей серии — 18,172 т уходили из БП 1491/1493 в чужой план, а у 1491/1493
остаток становился −18,172 т при полностью сошедшемся 1С.

**Контроль модели:** недоезд по всей компании (уехало минус приехало) должен быть
≈ 0. Сейчас 0,000 т при перемещениях 276 890,086 т.

## 9. Возврат поставщику — отрицательный приход

Так его считает 1С: в отчёте «Остатки и движение товаров» возврат стоит в колонке
«Приход» со знаком минус. Пока он держался отдельным расходом, колонка «купили»
была брутто и не сходилась: по БП 1563 — 3 169,834 против 3 003,901 в 1С, ровно на
два документа возврата.

Нетто применяется **только к колонке прихода**. В остатке возврат по-прежнему
вычитается как расход: тождество (К − В) − Р = К − (В + Р) выполняется, только
если вычесть ровно один раз.

## 10. Единицы измерения

Тоннаж считается **построчно**: у одного кода в разных строках бывают разные имена
(дубли справочника) и разные единицы. Подбор справочника по имени из первой строки
завышал итог на 83,5 т.

т = 1, кг = 0,001, г = 1e-6. Если базовая единица «м», а «ЕдиницаДляОтчетов» = «т»
и заполнен коэффициент — делим на коэффициент. шт, компл, пар, л, м³, км, м², уп,
рулон **в тоннаж не превращаются вовсе**.

Единица — самостоятельный **разрез отчёта**: тонны · штуки · метры · литры ·
комплекты и т. д. Группируется только то, что переводится друг в друга: вес
(т/кг/г) и метры (м/пог.м/пм). Километры с метрами не смешиваются — 212 км стали
бы 212 метрами.

**Суммы разных разрезов не складываются.** Строка попадает в «тонны», если у неё
есть тоннаж, и в разрез своей единицы, если та не весовая. У номенклатуры с
заполненным коэффициентом это оба разреза сразу: 32 м и 0,218 т — один металл в
двух измерениях.

## 11. Склады и подразделения

Тип склада определяется **по номеру папки** справочника складов:

| Номер папки | Тип |
|---|---|
| 1–4 (Западная Сибирь, Юг, Пермь, Коми) | Заготовка, дивизион = регион |
| 5 | База, дивизион = имя базы |
| 6 | Ответхранение |
| 7 | Собственные склады |
| 8–10 (Механичка, Винтовые сваи, ЭЦН Чернушка) | **Цех** |

Разбирается номер, а не имя: в справочнике есть и «5.База Осенцы», и «5. База
Когалым». Папка 99 («Склады для табелирования») — служебная.

У старых складов подразделение в 1С не заполнено — вместо него вписано имя самого
склада. Без правила по папке 800+ складов становились «договорными площадками», их
закупка не попадала в заготовку, и у бизнес-плана на диаграмме не было прихода
вообще.

Договорная площадка опознаётся так: в имени склада есть **и** договор, **и** номер
БП. Ранние движения по площадке сводятся с настоящей серией того же БП по ключу
«номер договора + ведущий номер серии» — это подняло долю продаж с реальной серией
с 36,65 % до 46,34 %.

## 12. Остаток

**ОСТАТОК — сколько ещё лежит на складах и может быть продано.** Считается из тех
же построчных движений: приход минус расход по ключу «серия · вариант · склад ·
номенклатура», поэтому колонка складывается снизу вверх и есть на каждом уровне
дерева, вплоть до итога по лоту.

Внутренние потоки входят обеими сторонами: «приехало» кладёт металл на склад,
«уехало» снимает — на уровне склада это и есть наличие.

Отрицательный остаток означает, что расход в регистре больше прихода. Сейчас 379
ключей на −20 763,926 т; на уровне бизнес-плана — 51 план на −14 071,363 т, из них
«БЕЗ СЕРИИ» −12 343,438 т. Разбор причин — в отдельной справке.

**Обратный ход.** Якорь — фактический остаток на сегодня из файла остатков.
Движения отматываются назад: остаток на дату = факт + расход после даты − приход
после даты. Файл покрывает 91 склад из 1 642, поэтому сверяется только пересечение.

## 13. Диаграмма Ганта

Одна строка — один бизнес-план. Строится в **двух вариантах** из одного набора
узлов «проект · вариант серии · склад · класс единицы → месяц → потоки».

| | вариант 1 — заготовка | вариант 2 — вся компания |
|---|---|---|
| склады | только «Заготовка» | все |
| приход | купили (за вычетом возврата) | то же |
| расход | уехало за пределы заготовки · продали · недостачи · затраты | продали · недостачи · затраты |
| декомпозиция | проект → склады | проект → дивизион → подразделение → склад |

Держать оба варианта на одних узлах обязательно: иначе итог строки разойдётся с её
же разбором.

«Уехало» делится по складу-получателю: если получатель — тоже склад заготовки, это
переезд внутри периметра и вывозом не считается.

**Остаток берётся по полному обороту склада**, а не по потокам варианта: иначе у
1578 на складе «Сандибинское м/р» показывалось 160,815 т, хотя металл оттуда уехал.

Статус считается сам: в срок · с опозданием · просрочен · в работе · без плана.
Срок вывоза правится прямо в диаграмме, правки лежат отдельным файлом и не трогают
выгрузки 1С.

## 14. Оплаты за лом

Платёж привязывается к бизнес-плану по ГУИДу из заявки на расходование — тому же
ПроектГуид. Дата берётся из колонки «ДатаПлатежа»; если пуста — из имени
регистратора. Разница существенна: когда колонку заполнили, у 72 платежей она не
совпала с датой документа, у 11 — месяцем.

Бизнес-план проставлен не у всех платежей: 284 строки из 3 873. Остальные
привязать не к чему — выдумывать привязку по договору нельзя.

## 15. Постоянные автопроверки

Считаются при каждой сборке. `✓` сходится · `!` вопрос к данным 1С · `✗` ошибка
расчёта.

| Проверка | Смысл |
|---|---|
| обратный ход | остаток на дату = факт + расход после − приход после |
| продано > поступило | серия в продаже есть, прихода нет |
| уехало ≠ приехало по серии | серия сменилась в пути |
| **недоезд по компании ≈ 0** | контроль модели |
| **сумма позиций = прямой пересчёт по строкам** | контроль арифметики |
| оплаты привязаны к бизнес-плану | покрытие привязки |
| смешанные лоты без дробных хвостов | качество раскладки |
| остаток по движениям vs факт | покрытие якоря |
| позиции с бейджами «нет» / «вероятно» | на валидацию заказчику |

Две проверки, выделенные жирным, — это **инварианты**: если они разошлись, ошибка
в расчёте, а не в данных.

Сверх них — семь **контрольных примеров** (`tools/control_check.py`), приёмочный
тест сборки. Должно быть 7 из 7.

## 2. Чтение входа

`read_text_lines(path)` определяет кодировку **по всему файлу**, а не по окну:
окно режет многобайтовый символ. Фолбэк — цепочка cp1251-mojibake. Файл движений
310–320 МБ читается построчно.

Входы опознаются по шаблону имени, берётся самый свежий файл:

| Роль | Шаблон |
|---|---|
| движения (обороты регистра) | `СебестоимостьТоваровОбороты_*.csv` |
| остатки на сегодня (якорь) | `Остатки на складах *.xlsx` |
| номенклатура | `Номенклатура_*.csv` |
| серии (проект, контрагент, дата вывоза) | `СерииНоменклатуры_*.csv` |
| склады (папка верхнего уровня) | `Склады_*.csv` |
| производственные подразделения | `*Производственные_подразделения*.csv` |
| оплаты за лом | `ОплатаЗаЛом_*.csv` |
| ручные привязки | `overrides.json` |
| ручные сроки вывоза | `plan_dates.json` |

## 3. Проходы

Расчёт нельзя сделать за один проход: правила ссылаются на агрегаты, которых на
момент чтения строки ещё нет.

**Проход 1 — `scan_movements` (`src/pipeline.py:800`).** Один разбор 304 774 строк регистра,
из него строятся все карты:

| Структура | Ключ → значение | Для чего |
|---|---|---|
| `flow_rows` | список `FlowRow` | все движения построчно |
| `part_map` | (партия, код) → серия | ступень 5 каскада |
| `part_variant`, `part_variant_ser` | (партия, код[, серия]) → строка серии | подпись варианта |
| `lot_dist` | лот → компоненты серий | смешанные лоты |
| `mix_alloc` | (лот, код, rid) → раскладка | ступень 3, готовый ответ |
| `move_pair` | (документ, код[, партия]) → Counter(серия) | ступень 4 |
| `uniq_sklad_code` | (склад, код) → серия, если она одна | ступень 7 |
| `sklad_series` | склад → серия, если она одна | ступень 2 |
| `plat_proj` | имя площадки → проект | ступень 8 |
| `series_variants` / `series_variants_own` | проект → Counter(строк серии) | выбор подписи |
| `balance`, `purchased` | (склад, код) → количества | обратный ход |

`FlowRow` — класс с `__slots__` из 18 полей: на 304 тыс. строк экономия памяти
против словарей около 40 %.

**Проход 2 — сведение сторон перемещения.** Отдельный быстрый проход по
`flow_rows`: сперва разрешаются строки «уехало» (там серия чаще стоит в 1С), и
полученной картой опознаются «приехало». Без этого приход опознавался по
складу-получателю и возникал ложный недоезд.

**Проход 3 — рождение тоннажа.** Проход по документам переработки: считаются
суммы сырья и выпуска по (номер, дата, серия 1С). Документы, где тоннажного сырья
нет, а тоннажный выпуск есть, попадают в множество `birth_docs`.

**Проход 4 — основной.** Для каждой строки движения вызывается
`recover_series_parts`, результат раскладывается одновременно в: позиции, потоки
жизненного цикла, узлы Ганты, состав плана, строку `moves`, буферы автопроверок.

**Проход 5 — наследование при переработке** — итеративный: выпуск одного документа
становится сырьём другого. Число итераций ограничено и печатается в лог.

## 4. Каскад — контракт функции

```python
recover_series_parts(s, part_map, lot_dist, uniq_sklad_code, overrides,
                     edits_log, mix_alloc, move_pair, sklad_series, plat_proj)
    -> [(серия | None, количество, бейдж), ...]
```

Возвращается **список**: одна строка реализации может расщепиться между сериями
(смешанный лот). Сумма количеств в списке строго равна `s["qty"]` — это и
проверяет инвариант «сумма позиций = прямой пересчёт по строкам».

Ступени проверяются подряд, `return` на первой сработавшей. Стоимость каждой
ступени — O(1) поиск по словарю, кроме ступени 3, где раскладка уже готова
(`mix_alloc` посчитан заранее).

## 5. Ключи

| Что | Ключ | Почему так |
|---|---|---|
| бизнес-план | `ПроектГуид` (или `n:<норм. имя>`) | стабилен, «V»/«VS» сводятся |
| лот | `тип документа + номер` (+ дата для переработки) | номера повторяются между типами и годами |
| остаток | проект · вариант · склад · код | складывается снизу вверх |
| узел Ганты | проект · вариант · склад · класс единицы | иначе итог разойдётся с разбором |
| ручная привязка | документ + **лот** + код | у 2 839 пар «документ+код» внутри разные серии |
| сведение перемещения | документ + код + **партия** | документ двигает несколько серий сразу |

Гомоглифы (кириллица → латиница) сворачиваются **только в ключе**: 22С0371 ≡
22C0371, но для показа остаётся исходное написание, иначе «УЗД-87/25» превратится
в «YЗД-87/25».

## 6. Формат снимка

`out/sales_data.json`, 49,2 МБ, 19 секций:

| Секция | Что внутри |
|---|---|
| `meta` | 59 полей: период, итоги, пороги, словари формулировок, автопроверки |
| `S` | таблица интернированных строк — все повторяющиеся тексты по индексу |
| `items` | 7 869 позиций продаж: склад, код, серия, бейдж, qty, tonnes, mc, документы |
| `moves` | 304 388 движений **колоночным массивом** из 15 полей |
| `gantt` | 1 072 проекта: план, статус, узлы, своды по вариантам и единицам |

**Интернирование строк обязательно.** Строка движения — массив из 15 элементов,
где текстовые поля заменены индексами в `S`. Без этого снимок был бы в разы
больше нынешних 49 МБ и браузер бы его не потянул.

Схема строки движения (`meta.move_cols`):

```

```

## 7. Оболочка

Все колонки потоков считаются **в браузере** из `DATA.moves`, а не приходят
готовыми. Это принципиально: любой уровень дерева — направление, план, серия,
склад, номенклатура, документ — заполняет одни и те же колонки из одного
источника, поэтому суммы складываются снизу вверх и не могут разойтись.

`flowAgg()` строит четыре карты за один проход по 304 388 строкам:

```
BY_S  проект                          → {поток: сумма}
BY_V  проект + вариант                → {поток: сумма}
BY_W  + склад                         → {поток: сумма}
BY_C  + код                           → {поток: сумма}
ROWS  + код                           → сами строки (для документов)
W_OF  (проект+вариант) → склад        → суммы (склады без продаж)
CODES (проект+вариант+склад)          → множество кодов
```

Результат кэшируется **по каждой единице отдельно** (`_AGG_CACHE`, не более
четырёх): на вкладке «Серии (продано)» разные проекты смотрят в разных единицах,
и пересчитывать 304 тыс. строк на каждое раскрытие нельзя.

Режим единицы держится в `MEASURE_FORCED` и читается через `curMeasure()`:

* `null` — глобальный выбор (диаграмма Ганта, «Движения»);
* `'все'` — вкладка «Серии (насквозь)»: отбора нет, величина = родное количество;
* конкретная единица — вкладка «Серии (продано)», выбирается **у проекта**.

Дети дерева строятся **лениво, по клику**, поэтому обработчик восстанавливает
режим своего проекта перед построением и возвращает прежний после.

### Две поправки, которые нельзя потерять

* **возврат**: в `flowAgg` он вычитается из «купили» (нетто, как в 1С), поэтому в
  `BAL_OUT` оболочки его НЕТ — иначе вычтется дважды. В Python сальдо считается от
  сырых потоков, там он в `BALANCE_OUT` остаётся;
* **приход через разборку**: идёт и в «купили», и в «из резки», поэтому копится
  отдельным ключом `_born`, и `balanceOf` снимает дубль ровно один раз.

## 8. Инварианты

| Инвариант | Где проверяется | Значение |
|---|---|---|
| Σ количеств каскада = qty строки | автопроверка «сумма позиций» | Δ 0,000000 т |
| уехало = приехало по компании | автопроверка «недоезд» | 0,000 т |
| итог строки Ганты = сумма её разбора | общие узлы у вариантов | по построению |
| остаток складывается снизу вверх | один источник (moves) | по построению |
| приход − расход − потери − недоезд − остаток = 0 | тождество модели | по построению |
| сборка воспроизводима | `PYTHONHASHSEED=0` | снимок сходится до байта |

Последний проверяется при каждом деплое: снимок на сервере и локальный совпадают
по md5 после исключения штампа времени.

## 9. Сложность и узкие места

| Этап | Сложность | Время |
|---|---|---|
| чтение 320 МБ CSV | O(N) строк | ~8 с |
| `scan_movements` | O(N) с O(1) вставками в словари | ~6 с |
| наследование при переработке | O(N · итераций) | ~1 с |
| основной проход | O(N) × O(1) каскад | ~2 с |
| сериализация снимка | O(N) | ~3 с |
| `flowAgg` в браузере | O(N) на единицу, кэш | ~0,4 с |

Узкое место не расчёт, а **размер снимка**: 49,2 МБ JSON и 49,5 МБ HTML. Отсюда
интернирование строк, колоночные массивы и разреженная запись — пустые классы
единиц и нулевые месяцы не пишутся вовсе.

## 10. Чего в коде нет намеренно

* **Нет FIFO.** У строки продажи есть свой лот-партия, подбирать по датам не нужно.
* **Нет пропорционального деления по умолчанию.** Только точное количество и
  ёмкость; деление — крайний случай с пометкой.
* **Нет привязки по договору.** Под одним договором лежат десятки проектов.
* **Нет пересчёта штук в тонны.** Ни при каких обстоятельствах, кроме случая,
  когда 1С сама дала единицу для отчётов и коэффициент.
* **Нет выдуманного дивизиона.** Если из данных регион не следует, узел честно
  встаёт группой «—».

Каждый из этих пунктов оплачен найденной в данных ошибкой.
